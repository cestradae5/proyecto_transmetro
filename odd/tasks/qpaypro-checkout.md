# QPayPro hosted checkout for card recharges

Branch `feat/qpaypro-checkout` (from `main` after PR #84). Step 3 of the order agreed in `parada-ridership.md` L2: real card recharges through the QPayPro sandbox hosted checkout. Analysis decisions: Engram #2094; verified contract: Engram #2093 (official QPayPro WooCommerce plugin v2.2.2) and the sandbox probe in L5.

## Specs
- S1 (user, verbatim): "segun lo que lei esta seria la forma de implementar pormedio de checkout alojado [...] El flujo es servidor a servidor primero y redirección del navegador después: backend del trasnmetro registra la transacción en QPayPro, recibe un token, y redirige al usuario a la página de pago alojada por QPayPro." Corrected (L2): the API answers the token as a `checkoutUrl` (no 302 to a `fetch`), and the result comes back as a browser redirect to the relay URL, not as a server notification.
- S2 Config: the API reads `QPAYPRO_LOGIN`, `QPAYPRO_API_KEY`, `QPAYPRO_PRIVATE_KEY`, `QPAYPRO_BASE_URL` (default `https://sandboxpayments.qpaypro.com`), `API_PUBLIC_URL` (base of the relay and cancel URLs) and `USER_WEB_URL` (where the browser lands after paying). If any of login, api key, private key, `API_PUBLIC_URL` or `USER_WEB_URL` is missing, `POST .../payments` answers 503 "Los pagos con QPayPro no están disponibles." and stores nothing. Credentials never reach the SPA or the logs.
- S3 Start payment: `POST /citizen/cards/:numeroTarjeta/payments` (no auth) `{ monto, email }`. `monto` must be exactly one of 10, 25, 50, 100 (user: "Montos fijos", "Q10 / Q25 / Q50 / Q100"); `email` a valid email (max 100). Invalid body -> 400; unknown card -> 404 "La tarjeta no existe."; card not `ACTIVA` -> 409 (same message as the simulated recharge). Then:
  1. inserts one `tbl_transaccion_pago` `INICIADA` with `referencia_pago = "QPP-" + UUID` (server-generated), `monto_pago`, `moneda GTQ`;
  2. POSTs `multipart/form-data` to `{QPAYPRO_BASE_URL}/checkout/register_transaction_store` with every field the sandbox requires (L5): `x_login`, `x_api_key`, `x_type AUTH_ONLY`, `x_method CC`, `x_visacuotas no`, `origen PLUGIN`, `store_type woocommerce`, `custom_fields {"order_id": referencia}`, `x_invoice_num referencia`, `x_description "Recarga Transmetro <referencia>"`, `x_amount` with 2 decimals, `x_currency_code GTQ`, `products` (one line: the recharge), `x_freight 0`, `taxes 0`, `x_discount 0`, buyer `x_first_name "Consumidor"`, `x_last_name "Final"`, `x_company "C/F"`, `x_email` = email, fixed Guatemala address/phone fields, `http_origin`, `x_relay_url = {API_PUBLIC_URL}/citizen/payments/qpaypro/relay`, `x_url_cancel = {API_PUBLIC_URL}/citizen/payments/qpaypro/cancel?referencia=<referencia>`;
  3. on `{ estado: "success", data: { token } }` -> 201 `{ referencia, checkoutUrl: "{QPAYPRO_BASE_URL}/checkout/woocommerce?token=<token>" }`;
  4. on network error, timeout (15 s), non-200, or a body without a token -> the transaction becomes `ERROR` with `mensaje_respuesta` (QPayPro's message, credentials never included) and the API answers 502 "No se pudo iniciar el pago con QPayPro.". The email is sent to QPayPro only, never stored.
- S4 Relay: `GET /citizen/payments/qpaypro/relay?order_id&x_trans_id&x_amount&x_response_status&order_hash` (no auth, called by the payer's browser). Always ends with 302 to `{USER_WEB_URL}/?pago=<order_id>` (`?pago=desconocido` when `order_id` matches no QPayPro transaction). Before redirecting:
  - signature: `order_hash` must equal `sha256(order_id|x_trans_id|x_amount|x_response_status|QPAYPRO_PRIVATE_KEY)` (hex, compared in constant time, using the raw `x_amount` string); a mismatch or missing parameter changes nothing;
  - amount: `x_amount` must equal `monto_pago` (2 decimals); otherwise nothing changes;
  - status `1` -> in one DB transaction, locking the transaction row: `APROBADA`, `id_transaccion_qpaypro = x_trans_id`, `codigo_respuesta = x_response_status`, `fecha_confirmacion`, one `tbl_recarga`, `saldo + monto` on the card, one `tbl_comprobante` `numero_comprobante = "QPP-REC-<idRecarga>"`;
  - any other status -> `RECHAZADA` with `id_transaccion_qpaypro`, `codigo_respuesta`, `fecha_confirmacion`; no recharge, balance unchanged;
  - only from `INICIADA` or `EXPIRADA` (a signed approval that arrives after expiry still credits: the bank charged). A repeated relay for an `APROBADA`/`RECHAZADA` transaction changes nothing (exactly one recharge per payment).
- S5 Cancel (user: "EXPIRADA al volver"): `GET /citizen/payments/qpaypro/cancel?referencia=` (no auth): an `INICIADA` QPayPro transaction becomes `EXPIRADA`; any other state is unchanged; always 302 to `{USER_WEB_URL}/?pago=<referencia>` (or `desconocido`).
- S6 Status: `GET /citizen/payments/:referencia` (no auth) -> 200 `{ referencia, numeroTarjeta, monto, estadoPago, numeroComprobante | null, saldo }` (`saldo` = current card balance). Unknown referencia -> 404 "El pago no existe.". When the transaction is `INICIADA` and older than 10 minutes (user: "dejemos un tiempo menor como 10 mins aprox"), it first tries the QPayPro query (S7) and, if that cannot confirm it, marks it `EXPIRADA` before answering. No cron (L2).
- S7 Reconciliation (user: "SPA + admin"): a QPayPro transaction query that, given our transaction, returns approved/rejected/unknown. Signed approval -> the same credit as S4; rejected -> `RECHAZADA`; unknown -> unchanged. Used by S6 and by `POST /cards/:numeroTarjeta/payments/:referencia/verify` (staff, Bearer + `RECARGAS_REPORTES_CONSULTAR`; 401/403 otherwise; 404 unknown card or referencia of another card) -> 200 the S6 body. Which QPayPro endpoint supports this is not proven yet (T4 probes it, L4); if none can find a payment by our referencia, S7 answers "unknown" and only expiry applies.
- S8 Simulated recharge (user: "Conviven por flag"): unchanged behind `RECHARGE_SIMULATOR_ENABLED`, except that a client `referencia` starting with `QPP-` -> 400 (reserved for QPayPro). Card activity `origen` is `QPAYPRO` when the referencia starts with `QPP-` or the transaction has a QPayPro id.
- S9 SPA recharge (user: "Pedir solo email", "Montos fijos"): the recharge panel shows four buttons Q10, Q25, Q50, Q100 and an email input; "Pagar con QPayPro" is disabled until an amount and a valid email are chosen and while sending. On 201 the browser goes to `checkoutUrl`. API errors show their message. When `VITE_RECHARGE_SIMULATOR=true`, the existing simulated recharge stays available as a secondary option.
- S10 SPA result: on load with `?pago=<referencia>`, the SPA calls S6 and shows: `APROBADA` -> "Recarga exitosa", comprobante, amount and new balance; `RECHAZADA` -> "El pago fue rechazado."; `EXPIRADA` -> "Pago cancelado o expirado."; `INICIADA` -> "Estamos confirmando tu pago..." with a "Verificar de nuevo" button; `desconocido` or 404 -> "No encontramos el pago.". A "Volver" button clears the query string.
- S11 admin-web (user: "SPA + admin"): in the card detail recharges table, each `QPAYPRO` row in `INICIADA` or `EXPIRADA` has a "Verificar con QPayPro" button calling S7; the row updates with the answer; errors show their message.
- S12 Docs: API README (citizen), user-web README (env vars `VITE_RECHARGE_SIMULATOR`, flow), `apps/api/.env.example` keys without values, Postman requests for S3, S5, S6 and a guide to pay in the sandbox with a test card. UI copy in neutral Spanish, code in English.
